## 2. PayPal fit: documentation versus an actual sandbox run

1. **Invoice create + send + payment event — CONFIRMED in documentation.** PayPal’s [Invoicing webhook guide](https://developer.paypal.com/api/invoicing/webhooks/) gives sandbox create and send endpoints and names `INVOICING.INVOICE.PAID`; register the webhook on the same app that creates the invoice, verify its signature, and handle duplicate deliveries. [Troubleshooting](https://developer.paypal.com/invoicing/troubleshooting).
   **CONFIRMED caveat:** PayPal says the paid event can mean partial, pending, or paid; its sandbox example also records an external bank transfer. Therefore the event name alone does not prove a completed PayPal capture. Read back the invoice and payment evidence, verify amount, currency, payee and final state, and define whether recorded external payments qualify before releasing a file. [PayPal invoicing customization](https://developer.paypal.com/platforms/invoicing/customize/), [webhook example](https://developer.paypal.com/api/invoicing/webhooks/). **UNVERIFIED:** this team’s actual sandbox credentials, event payload, and end-to-end unlock.

2. **Agent Toolkit tools and limits — CONFIRMED in PayPal’s [toolkit repository](https://github.com/paypal/agent-toolkit).** Its documented tools include `create_invoice`, `send_invoice`, `get_invoice`, `create_order`, `get_order`, and `pay_order`; the latter is described as processing an authorized order, not permission to bypass buyer approval. It also lists recurring invoice series. Its TypeScript configuration allows specific action flags and `context: { sandbox: true }`. Expose only required create/read/send actions rather than all tools; execute allowed writes through server-controlled wrappers. **UNVERIFIED:** a built-in per-invoice dollar threshold. **Recommendation:** enforce creator, recipient, currency, amount, scope, expiration and approval limits in deterministic server code for every actual call, including scheduled sends; require a fresh human approval above the cap. The toolkit action flags are tool exposure, not proof that a dollar policy is enforced.

3. **Orders v2 guest card — CONFIRMED as a documented sandbox path, conditional on eligibility.** PayPal’s [Checkout integration](https://developer.paypal.com/platforms/checkout/standard/integrate) creates an Orders v2 order and describes guest card checkout and testing with generated sandbox cards. Availability and layout can vary by merchant, buyer, country and account features. **UNVERIFIED:** that this team’s specific sandbox account shows the guest-card option or completes a card capture.

4. **Payouts for collaborators — CONFIRMED as a documented sandbox capability.** [PayPal Payouts](https://developer.paypal.com/payouts/use-payouts/overview) says developers can set up and test in sandbox while live access is under review; it pays multiple recipients and is funded from the sender’s PayPal balance. The [Payouts request reference](https://developer.paypal.com/api/payments.payouts-batch/v1/definitions/create_payout_request/) documents duplicate batch ID protection and says sandbox does not support phone recipients. A collaborator split is a separate outgoing payout after receipt, not proof that the original checkout automatically splits at capture; account access, available balance, recipient eligibility, fees and payout status must be checked. **UNVERIFIED:** this sandbox app’s Payouts entitlement or successful payout.

5. **Renewal — CONFIRMED:** the [toolkit](https://github.com/paypal/agent-toolkit) lists recurring invoice series that generate and send invoices on a schedule. **UNVERIFIED:** that it matches a particular one-time license expiry, or that the client consented to an automatic extension. An invoice is a request for payment, not an automatic successful charge. Do not extend rights or release new files until the required consent and verified payment state exist.

## 3. Why judges might choose UseRight Agent over Clause & Pay

These six are **UNVERIFIED judgments about a proposed product**, not claims about judges or completed UseRight functionality. Clause & Pay’s described baseline is its [opened project page](https://devpost.com/software/clause-pay); [event prizes](https://paypalaihackathon.devpost.com/) include Best Use of PayPal + AI and Best Use of Agentic Commerce.

**Three reasons to choose it, if demonstrated:**
1. A clear creator problem: compare the requested channel, territory and duration against a limited license and calculate only the gap from the creator’s rate card.
2. A visible commercial outcome: a properly paid license unlocks the actual file and rights receipt, and expanded use can produce a second, traceable payment.
3. A bounded agent can send a small invoice without another click while escalating above the creator’s threshold, showing useful autonomy and control together.

**Three reasons not to choose it:**
1. Clause & Pay already describes contract quotation checks, acceptance evidence, approval and a paid webhook; its more complete demonstrated workflow could beat a partially built licensing concept.
2. Ambiguous briefs, incorrect extraction, wrong recipients or an over-broad auto-send policy can damage creator trust; an amount cap alone does not establish correct rights.
3. Multi-channel intake, payment-state checks, renewal consent and optional payouts add failure points. A narrow, reliable demo may score better than a wider workflow with simulated or unverified payment steps.

**Practical recommendation — UNVERIFIED design judgment:** Demo one text brief, one creator-defined rate card, one verified sandbox payment and one re-license; add channels and payouts only after that path works.
